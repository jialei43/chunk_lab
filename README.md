# chunk-lab

RagFlow MinerU 切分逻辑的离线实验室。用于持续发现切分缺陷、量化改动效果、防止回归。

## 启停服务

```bash
cd /Users/jialei/Desktop/RagFlow/chunk-lab

./serve.sh start     # 后台启动，然后打开 http://127.0.0.1:5099
./serve.sh stop      # 停止
./serve.sh restart   # 重启
./serve.sh status    # 查看是否在运行，以及实际的热加载模式
./serve.sh log       # 跟随查看日志（Ctrl+C 只退出查看，不影响服务）
```

前台运行（Ctrl+C 停止）：`./run.sh serve`
换端口：`CHUNKLAB_PORT=6000 ./serve.sh start`

**改代码不必手动重启**：默认开启热加载，改 `labkit/` 下的 Python 或前端页面后约 2 秒自动生效。

热加载可在启动时指定，前台后台都支持：

```bash
./serve.sh start --no-reload        # 后台启动并关闭热加载
./serve.sh restart --reload         # 显式开启（默认即开启）
CHUNKLAB_RELOAD=0 ./serve.sh start  # 环境变量方式，可 export 长期生效
./run.sh serve --no-reload          # 前台运行时同样可关
```

命令行参数优先于 `CHUNKLAB_RELOAD`。关掉热加载能省下重载器多起一个进程、模块重复加载十几秒的开销，代价是改代码后必须 `./serve.sh restart` 才生效。`./serve.sh status` 显示的模式从运行中进程的命令行反查，不受当前环境变量影响。

常用命令：

```bash
./run.sh eval                    # 全量评估，出报告
./run.sh eval --compare          # 改代码后与基线对比
./run.sh runs                    # 看历史轮次
./run.sh inspect <样本> --chunk N # 复现单个切片及其前后文
./run.sh crawl <列表页URL> --dry-run  # 从网页抓取文档（先试跑）
```

## Web 控制台

启停命令见文首。控制台有五个页面：

| 页面 | 作用 |
|---|---|
| **概览** | 一键运行评估；轮次对比（任选两轮，非只能比基线）；趋势图看各类问题随轮次的累计变化；历史轮次列表可设基准／打备注／删除；问题分布与逐样本统计 |
| **切片预览** | 选一个样本，逐块查看实际切分结果，有问题的切片按严重度标色并附证据 |
| **语料库** | 当前语料清单 |
| **网页抓取** | 给定列表页自动翻页下载文档，可直接送去解析入库。默认遵守 robots.txt、串行带间隔 |
| **解析文件** | 上传文件调 MinerU 解析，产物落在实验室目录、与生产分开，解析完自动入库。支持一次多选批量上传，参数整批共用 |
| **添加语料** | 扫描本机 MinerU 产物，勾选导入。已导入的自动标灰，可按文档名筛选 |

顶栏「切分配置」的字段与知识库配置页逐项对应，对评估和切片预览同时生效。

解析任务（无论来自「解析文件」的批量上传还是「网页抓取」的批量解析）在服务端**串行执行**，同一时刻只跑一个：MinerU 是本机单实例服务，并行跑多个解析会把显存与内存打满，整体反而更慢。等待中的任务在列表里显示「排队中」，其中一个失败不影响后续任务继续执行。

服务只监听回环地址，是开发时工具。基于 ragflow 虚拟环境里已有的 Flask，前端零构建、无外部依赖。

`serve.sh` 以端口占用而非 PID 文件判断状态，停止时结束**全部**占用该端口的进程——热加载下 Flask 重载器有父子两个进程，只杀子进程父进程会立刻重新拉起，看着停了实际没停。

## 原文对照支持哪些格式

预览页左侧显示原文，与右侧切片对照。点切片即在原文里定位。

| 格式 | 原文显示 | 点切片定位 | 说明 |
|---|---|---|---|
| PDF | 直接渲染 | **框出精确区域** | 块带 bbox |
| PPTX / DOCX / XLSX | 转 PDF 后渲染 | 翻到对应页 | 块只有页码、无 bbox |
| PNG / JPG 等图片 | 直接显示 | 框出精确区域 | 块带 bbox |

Office 文档由 LibreOffice 转成 PDF，复用同一套视图（缩放、翻页、定位、截图），
不必为每种格式再写一遍渲染。转换结果按源文件修改时间缓存：首次几秒，
之后毫秒级。没装 LibreOffice 时界面会提示 `brew install --cask libreoffice`。

图片刻意**不转 PDF**——转一道既糊又慢，而且图片的 MinerU 块本来就带 bbox，
直接显示才能做精确定位。

**MinerU 给 Office 块的坐标是退化值**（形如 `[2, 0, 0, 1, 1]`，宽高为零），
所以只能定位到页、框不出块的位置。DOCX 更受限：它的 `page_idx` 全是 0，
连页码都对不上，只能显示原文。这是解析阶段的既有事实，不是这里的取舍。

图片样本能显示原文，但用 `naive` 切分器**切不出切片**——生产的 naive 只支持
pdf/xlsx/doc/docx/txt。要切图片得把「解析方法」改成 `picture`。

## 改完代码怎么看效果

```
改代码 → 运行评估（全量切一遍，按轮次存下来）→ 预览页选那一轮看
```

评估会把**每个样本的完整切分结果**存进该轮快照：正文、面包屑、页码、
版面坐标、以及那一轮检出的全部问题。预览页顶部的「查看」下拉可以选任意
一轮，读的是文件，不重新切分——上千切片的样本实测 3.5 秒，实时切分要 14 秒。

选历史轮次和实时切分**看到的东西完全一样**：问题标注、原文对照、点切片
在 PDF 上定位高亮、裁图，全都可用。这是刻意的——快照要能替代实时切分，
就不能是个只有文本的降级版本。

每一轮都记着自己的代码指纹，下拉里直接标出「= 当前代码」还是「代码已变」。
改完代码没跑评估时，看着旧快照会误以为改动没生效，这个标注就是防它的。

删除某一轮会连带删掉它的快照、切分文本、Markdown 报告与索引记录；
若它正是当前基线，指针一并清空。

### 改检测规则的顺序

规则是靠人工标注来验证的，不是靠感觉。正确顺序：

```bash
./run.sh guard              # 1. 改之前跑一次，记下基准
# ... 修改 labkit/detectors.py ...
./run.sh guard              # 2. 改完再跑，比对结果
```

护栏把标注变成断言：标为**误报**的应不再命中，标为**确认**的应仍能命中。
只有出现「回归」才算失败——那说明改动碰坏了本来能检出的东西；「待修正」是
还没改到的待办，「仍未覆盖」是人工提出、规则尚未实现的需求，都不该拦住一次改动。

标注按正文摘要而非序号定位：切分参数一改序号就整体错位，第 10 条标注会落到
完全不相干的第 10 个切片上。找不回原文时会记为「标注已失配」，提示该条需重做。

### 所有数字都按版本核对

「规则质量」页顶部可选**基于哪个版本**统计：当前代码（实时切分核对）或任意一轮快照。

这不是可有可无的开关。标注是跨版本累积的——上周标的一条误报，这周可能已经
修好了。直接数标注文件会有两个后果：修好的误报照样压低准确率，等于拿旧账
算现在的成绩；生成的任务书里还会列着已经不存在的问题，让人去改一个空气。

所以统计不数标注，而是**逐条核对**：标为误报的在这个版本下是否还在报、
标为确认的是否还能检出。核对结果分成几档：

| 计数 | 含义 |
|---|---|
| 仍在误报 | 该版本下还没修好的，**这才是待办** |
| 已修复 | 曾标为误报、该版本已不报，不计入准确率 |
| 仍能检出 | 确认是问题且仍能检出 |
| 回归 | 曾能检出、该版本检不出了，**唯一算失败的一档** |
| 标注已失配 | 按正文摘要找不回切片，需重做，排除在统计外 |

选历史轮次时读快照核对，秒级完成；选「当前代码」要把已标注样本全部重切，
样本多时要等几分钟。

### 单条规则的优化报告

「规则质量」页每条规则后的「生成优化报告」，产出一份可直接拿去改代码的 Markdown：
规则的**当前实现**（函数源码与相关正则常量，从运行中的模块直接取，不会与代码脱节）、
每条反例**此刻的真实命中证据**（重跑切分取得，不是标注时的旧值）、人工判断的原因、
以及改完怎么验证。整段复制给模型即可动手改。

实测 `markdown_residue` 的报告一眼看出问题：8 条误报的命中证据全是 `__name__`，
即 Python 的 dunder 被 `__[^_\n]+__` 当成了 markdown 强调。

页面上所有统计数字都可点击：点误报数看全部反例、点需求次数看在哪些切片上提的，
点任意一条跳回切片预览并定位到那块正文。框选出来的区域单独汇总一块，
点一条跳回原文视图并滚动到该区域——它不属于任何切片，不会出现在规则统计里。

一条规则命中上百个切片时，逐条判定不现实。在切片预览里点某个问题类型筛选后，
筛选栏下方会出现整类批量判定条，可一次把该类下**尚未标注**的切片全标为误报或
全确认是问题，也可整批撤销。已标注的切片一律跳过——批量是为了省去重复点击，
不该悄悄推翻此前逐条细看后给出的判断；界面上会直接标出「N 个已标注，写入时跳过」。

批量写入的问题类型记为**当前筛选的那一类**，而不是切片命中的第一条规则。一个切片
可以同时命中多条规则，按命中顺序归类会把判定算到别条规则头上，污染准确率统计。

常用选项：

| 选项 | 说明 |
|---|---|
| `--case <id>` | 只评估指定样本，可重复，用于针对单个文档快速迭代 |
| `--children-delimiter` | 父子分块分隔符，**对切分粒度影响极大**，见下文 |
| `--chunk-token-num` | 覆盖 token 预算 |
| `--top N` | 每类问题展示 N 条样例证据 |

全量评估 13 个样本、5608 个原始块约 **14 秒**——同样的内容走真实解析要几十分钟，这个差距就是整套方案能持续迭代的前提。

`run.sh` 固定使用 `ragflow/.venv/bin/python` 的绝对路径，不依赖当前终端激活了哪个虚拟环境，且**绝不使用 `uv run`**（避免触发 `uv.lock` 解析并静默改写环境）。

## 设计要点

离线驱动**不写任何 stub**，直接构造真实的 `MinerUParser` 并调用生产函数 `chunk_mineru_blocks`，保证离线结论与线上行为零偏差。三条依据均已在 ragflow 源码中核对：

1. `MinerUParser.__init__` 只赋值属性、不做网络调用，可无参构造；
2. `chunk_mineru_blocks` 内所有 `crop` 调用点都有 `page_images` 守卫，不提供页面图像即走"无截图"分支，与生产的 Office 路径行为一致；
3. `tenant_id` 传 `None` 时 `get_vision_model` / `get_chat_model` 直接返回 `None`，不加载 LLM、不 import `api.db`、不连数据库——因此离线结果确定可复现。

## 阶段一：保真度验证结论（已通过）

用 `tmp/pdfs/mineru_two_column_e2e_output/` 的双栏 PDF 产物离线重放，与历史生产 e2e 结果 `mineru_two_column_e2e_chunks/summary.json` 逐块比对：

- 喂给切分器的 blocks 完全一致（23 个，`text_level` 分布相同），确认产物层无偏差；
- 父块正文与生产 chunk 逐字吻合（如 `> 2 评估方法` + `[P03] 本样例采用 A4 纵向页面…`）；
- 唯一差异是面包屑分隔符（生产为换行、当前代码为 ` > `），属 summary.json 是历史产物、面包屑格式后来改过的代码演进，非离线偏差。

PPTX 路径同样验证通过（40 chunk，含 9 个表格，位置/页码/面包屑齐全）。

### 关键发现：`children_delimiter` 是切分粒度的主开关

同一份产物，仅改这一个参数，结果差异巨大：

| `children_delimiter` | chunk 数 | 平均长度 | 说明 |
|---|---|---|---|
| 空 | 14 | 127 | 每个原始段落独立成块 |
| `\n` | 14（子块） | 128 | 5 个父块，按换行拆成 14 个子块 |
| `‡`（正文中不存在） | 5 | 306 | 子拆分不切割，即父块粒度 |

机制在 [`mineru_chunker.py:1494-1498`](../ragflow/rag/app/mineru_chunker.py#L1494) 的合并边界判定：默认模式下"同标题的不同原始段落也必须独立成块"，父子模式下只有标题变化才断开。

两个必须记住的契约：

- **离线驱动必须复刻 `naive.py` 的 `children_delimiter → 正则` 转换**（含 `unicode_escape` 还原与反引号自定义分隔符），否则同一份产物会得到与生产迥异的结果；
- **父子模式下返回的全部是子块**，父块全文挂在 `mom_with_weight` 字段上。评审器必须据此区分口径，否则会把子块的短长度误判为切分过碎。

## 阶段二～三：检测器、语料库与回归防护（已完成）

### 语料库

13 个样本、5608 个原始块，覆盖 PDF（双栏／法律／年报／专利）、PPTX、DOCX、XLSX。

同一文档的重复解析副本只收一份，但**同源不同 backend 的产物刻意保留为对照**（`law_bill_hybrid` 137 块 vs `law_bill_vlm` 111 块）——块数差异这么大，切分逻辑对它是否鲁棒本身就该被测。

### 检测器

16 个规则检测器，全部在 `detectors.py` 的 `ALL_DETECTORS` 登记表中，新增只需追加一项。

严重度分三档：`high` 内容层缺陷（句子截断、表格破损、表格被拆散、乱码、噪声残留）、`medium` 质量问题（碎片块、内容重复、列表被拆散、指代缺失上下文、图注公式脱离、标题孤块、标题与正文分离、markdown 残留、图片空壳）、`low` 体验问题（缺面包屑、缺定位）。

曾有「字间空格」检测器，经判定属正常排版（封面艺术字、字间距样式）已移除。

### 首轮调优：651 → 258 条

### 回归防护：运行历史

每次评估都存成**不可变快照**（一个 run），任意两轮之间都能对比。基线不再是一份独立数据，只是**指向某一轮的指针**——因为单一基线文件一旦更新，之前的历史就没了，无法回答「这几次改动累计效果如何」「哪一次引入了这个回归」。

```bash
./run.sh eval --label "修复 DOCX markdown 残留"   # 跑一轮，自动存入历史
./run.sh runs                                    # 看全部历史轮次
./run.sh runs --compare baseline latest          # 对比任意两轮
./run.sh baseline <run_id>                       # 把某轮设为基准（不必重跑）
```

轮次引用支持三种写法：`baseline`（当前基准）、`latest`（最新一轮）、具体 `run_id`。

**每轮记录代码指纹**——对 `mineru_chunker.py` / `mineru_parser.py` / `mineru_noise.py` 做联合内容哈希。这比 git commit 更准：改了没提交时 commit 不变，只有哈希会变。没有它，历史轮次不知道对应什么代码状态，对比就失去意义。

**对比前自动校验可比性**。参数或语料不同的两轮，数字并列会直接导致误判，因此会显式警告：

```
⚠️  这两轮不完全可比：
    · token 预算不同（512 vs 256），切分粒度本就不同，数字不能直接归因于代码改动
    · 两轮的被测代码完全相同，指标差异并非来自代码改动
```

这两条合起来就说清了：那次「劣化 +16」根本不是代码问题。

### 切分文本快照：为什么必须存

每轮同时保存**当时的切分文本**（`runs/<id>.chunks.gz`）。这不是可选项：离线驱动调的是**当前**代码，代码一改，旧轮次的切分结果就再也无法重现。不存下来，历史轮次只剩统计数字，看不到那时文本被切成了什么样。

体积可控：3272 个切片的完整正文，gzip 后约 **335 KB**，跑 20 轮才 6.7 MB。

有了它才能做**文本级对比**——问题数只能说明"多了 6 条截断"，文本对比才能说明"边界从哪挪到了哪"。实测 token 512→256：

```
切片 89 → 97，内容未变 84，变化 13
[修改] #4 → #4
  前：附件4\n<table>…
  后：附件4（分片 1/2）\n<table>…
```

表格被拆成了「分片 1/2」「分片 2/2」，一眼可见。配对同样按内容而非序号——按序号比会把 89 个切片几乎全算成变化。

切片预览页也可切换数据来源：**实时切分（当前代码）** 或**任一历史轮次的快照**。

存储上，`runs/*.json` 是报告（含 findings 明细），`runs/*.chunks.gz` 是切分文本，两者体积大不入库；`runs/index.json` 是轻量索引（含各轮各检测器命中数，**入库**），所以指标趋势可以长期追溯。

对比同时输出**命中数**与 **chunk 数**两个维度，缺一不可。实测把 `chunk_token_num` 从 512 降到 256：

```
xlsx_9sheet    命中 0→0 (+0)    chunk 65→208 (+143)
```

命中数完全没变，切分粒度却暴增 3 倍。只盯问题数会彻底漏掉这类回归。
