# chunk-lab

RagFlow MinerU 切分逻辑的离线实验室。用于持续发现切分缺陷、量化改动效果、防止回归。

## 启停服务

```bash
cd /Users/jialei/Desktop/RagFlow/chunk-lab

./serve.sh start     # 后台启动，然后打开 http://127.0.0.1:5099
./serve.sh stop      # 停止
./serve.sh restart   # 重启
./serve.sh status    # 查看是否在运行，以及实际的热加载模式
./serve.sh log       # 跟随查看日志（Ctrl+C 只退出查看，不影响服务）
```

前台运行（Ctrl+C 停止）：`./run.sh serve`
换端口：`CHUNKLAB_PORT=6000 ./serve.sh start`

**改代码不必手动重启**：默认开启热加载，改 `labkit/` 下的 Python 或前端页面后约 2 秒自动生效。

热加载可在启动时指定，前台后台都支持：

```bash
./serve.sh start --no-reload        # 后台启动并关闭热加载
./serve.sh restart --reload         # 显式开启（默认即开启）
CHUNKLAB_RELOAD=0 ./serve.sh start  # 环境变量方式，可 export 长期生效
./run.sh serve --no-reload          # 前台运行时同样可关
```

命令行参数优先于 `CHUNKLAB_RELOAD`。关掉热加载能省下重载器多起一个进程、模块重复加载十几秒的开销，代价是改代码后必须 `./serve.sh restart` 才生效。`./serve.sh status` 显示的模式从运行中进程的命令行反查，不受当前环境变量影响。

常用命令：

```bash
./run.sh eval                    # 全量评估，出报告
./run.sh eval --compare          # 改代码后与基线对比
./run.sh runs                    # 看历史轮次
./run.sh inspect <样本> --chunk N # 复现单个切片及其前后文
./run.sh crawl <列表页URL> --dry-run  # 从网页抓取文档（先试跑）
```

**本仓库完全独立，不属于 ragflow 的版本管理。**

- `/Users/jialei/Desktop/RagFlow/` 本身不是 git 仓库，唯一的仓库是它下面的 `ragflow/`（以及 `lzcj_web/`）。
- 本目录与它们平级，物理上不在任何一方的工作树内。在 `ragflow/` 下执行 `git status` / `git add -A` **看不到本目录的存在**——不是靠 ignore 规则挡住，是根本不在范围内。

## 数据目录（在仓库之外）

语料、历史轮次、报告、MinerU 解析产物全部存在**仓库之外**，默认 `~/MinerU/chunk_lab/`：

```
~/MinerU/chunk_lab/
├── corpus/       语料（含 middle.json，实测 20MB+）
├── runs/         历史轮次快照与切分文本
├── annotations/  人工标注，按版本分子目录：<版本>/<样本>.json
├── reports/      Markdown 评估报告
├── baselines/    基准指针
├── mineru_out/   MinerU 解析产物（与生产的输出目录分开）
└── uploads/      上传的原始文件
```

`annotations/` 下每个版本一个目录，互不影响；升级前那批不带版本的平铺标注文件
会在首次启动时自动收编进最新版本，原文件挪到 `annotations/_migrated_backup/` 保底。

**判为「误报」的问题不再计入后续评估**：每轮评估在继承完标注之后，会把人工判定为
`false_positive` 的条目标记为忽略——问题总数、各检测器命中数、终端报告、Markdown 报告
与界面标色都不再算它们，终端会如实提示「已忽略 N 条人工判定为误报的问题」。
判定过一次就不该每轮重新甄别同一批噪声，否则真正的回归会被淹没。

两点设计取舍：

- **明细保留不删**，只多一个 `ignored` 标记。判定本身也可能是错的，留着才能回溯当初为什么忽略它。
- 标注若指明了检测器，只忽略那一条规则；没指明则忽略该切片上的全部问题。同一切片上
  **其他规则**报出的问题照常计入。

继承源默认取上一轮评估。历史轮次被清理过时（`runs/` 被清空）会自动回退到最近一个存有
标注的版本目录——判定是人一条条看出来的，不该随历史清理一起报废。

这样安排是因为这些数据体积大且持续增长，留在仓库内会让 IDE 索引整个项目时明显变慢。仓库内只保留代码（约 500KB）。

修改位置，两种方式，优先级从高到低：

```bash
# 1. 环境变量，适合临时切换
CHUNKLAB_DATA_DIR=/path/to/data ./run.sh eval

# 2. 本机配置文件（复制 labconfig.example.json 为 labconfig.json，不入版本管理）
{ "data_dir": "~/MinerU/chunk_lab" }
```

当前生效的路径在 Web 控制台的「切分配置」弹层顶部可以看到。

## 增强项：表格摘要、图片 VLM 描述、艺术字兜底

这三项都要调模型，而实验室本身不属于任何租户——切分器按租户去库里查模型配置，
拿不到就一律降级为空结果。因此需要**借用一个真实租户的模型授权**：

```bash
# 环境变量优先
CHUNKLAB_TENANT_ID=<租户id> ./run.sh eval

# 或写进 labconfig.json（不入版本管理）
{ "tenant_id": "<租户id>" }
```

租户必须满足：`tenant` 表的 `img2txt_id` / `llm_id` 在 `tenant_llm` 里有**对应且
api_key 非空**的授权行。不满足会报 `Model(xxx@yyy@None) not authorized`——
注意这个报错不代表模型坏了，只代表这个租户没被授权用它。可以这样挑一个：

```sql
select t.id, t.name from tenant t
join tenant_llm v on v.tenant_id=t.id and concat(v.llm_name,'@',v.llm_factory)=t.img2txt_id and v.api_key<>''
join tenant_llm h on h.tenant_id=t.id and concat(h.llm_name,'@',h.llm_factory)=t.llm_id     and h.api_key<>''
limit 1;
```

配好后在 Web 控制台「切分配置」里能看到三个开关（图片 VLM 描述、表格 LLM 摘要、
艺术字兜底重识别），也能看到租户与模型是否真的可用。

**三个开关一律默认关闭**，需要时手动勾选。这与生产的取舍不同：生产是一次性入库，
多花几分钟换更好的召回是划算的；而实验室要反复重放同一批语料看切分边界的变化，
一轮评估的绝大部分时间和费用都花在这三项上（见下面的代价），可它们产出的是
图片描述与表格摘要**文本**，对「段落怎么合并、边界切在哪里」毫无影响。
要评估图片描述质量或表格摘要效果时再开——那是另一类实验。

**配图从哪来**：生产的 `_read_output` 把 content_list 里的相对 `img_path`
绝对化为「content_list 所在目录 / img_path」，所以语料目录里必须有 `images/`。
导入语料时会自动把它**软链**到 MinerU 产物目录（整套语料图片约 600MB，
复制纯属浪费，且两者同在数据根下、生命周期一致）。产物目录被清理时软链失效，
行为退回「无配图」，不会报错。

**代价，用之前必须知道**：

- 调用量按块算——每张图一次 VLM、每张表一次 LLM。当前 39 个样本是
  400 图 + 3001 表 ≈ **3401 次调用**，表格摘要是绝对大头。串行跑完全量评估要按小时计。
- **切片预览也会调**。预览一个 400 张表的年报＝400 次对话调用，实际不可用。
  看这类样本前先在「切分配置」里关掉表格摘要。
- **结果不可复现**。模型每次输出都不同，图片/表格 chunk 的正文每轮都变，
  这些块上的人工标注会每跑一轮就失配一次——跨版本继承靠的是正文摘要匹配。
  想要可比的版本对比，就把增强项关掉再跑。

  > 上面三条代价中，**前两条已被结果缓存基本抹平，第三条被反转为「可复现」**，
  > 见下一节。开启增强项的门槛因此低了很多，但首轮的时间与费用依然要付。

### 模型调用结果缓存（默认开启）

三个增强项最终都落到 `LLMBundle` 的两个方法上——`describe_with_prompt`
（图片描述、艺术字兜底）与 `async_chat`（表格摘要）。它们的输入完全确定、
输出是纯文本，是标准的纯函数，因此结果被缓存进 Redis 永久保留。

实测：

- **表格摘要**（`复杂表格样例_9sheet`，9 张表）：冷跑 9 次调用 28.0s →
  热跑 **0 次调用 0.3s**，切分结果逐字节一致
- **图片描述**（`1225464824.PDF`，752 chunk / 2 图块）：冷跑 4 次 VLM 调用 21.0s →
  热跑 **0 次调用 14.8s**，图片 chunk 正文逐字一致。VLM 净耗时 6.2s 被完全消除，
  余下 14.8s 是传 `pdf_path` 后渲染页面图的固定开销，与模型无关

命中还有一个附带好处：不再写 `tenant_llm.used_tokens`，热跑完全不消耗 token。

**图片能不能加载，取决于文档类型**：`_load_block_image` 的三级降级里，预载字节和磁盘
`img_path` 在实验室里都不可用（前者只在 `parse_file` 里发生、桥接层走的是 `_read_output`；
后者指向已清理的原产物目录、软链失效），实际生效的只有第三级「按 bbox 从页面渲染图裁剪」。
所以 **PDF 传了 `pdf_path` 就能出图**，而 Office 块无 bbox，目前仍是「无配图」。

**实现方式**：`labkit/vlmcache.py` 在实验室进程内用运行时包装替换那两个方法，
**ragflow 源码一行未动**，生产的 task_executor 是另一个进程，完全不受影响。

**缓存键**由 `模型名 + 方法名 + 提示词 + 载荷指纹` 四段算 sha256，四段缺一不可：

- 载荷指纹是核心区分位；跨文档重复的图（页眉 logo）指纹相同，自动共享，命中率更高
- 提示词必须进键——同一张图会被「图片描述」和「艺术字兜底」两条链路分别请求，
  两者提示词不同，不进键就会互相读到对方的结果
- 模型名进键，换 VLM 后不会读到旧模型的产出

刻意**不用**「文档名 + 页码 + bbox」这类位置键：bbox 会随解析参数与双栏修复漂移，
键不变而图变了就会读到错图的描述且毫无察觉。内容指纹最坏只是 miss 重跑一次。

**坏结果不入库**：空结果、以及 chat 链路遇错时返回的 `**ERROR**` 字符串
（它不抛异常，`_table_summary` 正是据此判定失败）都会被挡住，
避免一次偶发故障被永久固化。

**存储**：复用 ragflow 的 Redis 实例（连接参数自动读 `conf/service_conf.yaml`，
不必重复配密码），但**逻辑库另开 db=3**，不与生产的消息队列混放。
Redis 连不上、超时、数据损坏一律降级为直连模型，绝不阻塞评估。

```bash
./run.sh cache                 # 查看条目数、占用、各样本用量
./run.sh cache clear           # 全清
./run.sh cache clear --sample 复杂表格样例_9sheet__vlm   # 只清一个样本
CHUNKLAB_VLM_CACHE=0 ./run.sh eval    # 临时跑一轮不吃缓存的对照实验
```

**必须知道的两点**：

1. **条目永久保留，不设 TTL**。因此改了切分器里的提示词常量后，旧条目既不会被读到
   （键变了）也不会自动消失，会变成死数据——`cache clear` 是必要的运维手段，不是可选项。
   Redis 实例侧的 `allkeys-lru` 是唯一兜底：实例限额 128MB，而整套语料的缓存约几 MB，
   实际不会触发驱逐。
2. **缓存让增强项结果变得可复现**，这正是回归对比想要的；但当你要专门评估
   *VLM 描述质量本身* 时，先 `cache clear`，否则永远看到同一份旧输出。

### 评估是后台任务，被打断能续跑

点「运行评估」不再是同步等一个请求跑完，而是创建一个**后台任务**：请求立刻返回，评估在后台逐个语料跑，**每跑完一个就把结果落盘**。历史轮次表格顶部会多出一行「进行中」，点「详情」进「评估进度」页看逐语料状态。

这么做是因为一轮全量评估要十几分钟，而这段时间里只要进程重启，跑完的几十个语料就连同结果一起消失。**改一次 `labkit/` 下的代码就会触发热加载重启**，开发时这是家常便饭——2026-08-09 上午就发生过一次：一轮评估跑到第 35 个语料，`evaluate.py` 被改了一下，Flask 重载器重启进程，整轮白跑，界面上只看到一句没头没尾的「评估失败」。

现在这种情况会被认成「已中断」，点**续跑**从断点接着跑剩下的语料：

| 状态 | 含义 | 可做什么 |
|---|---|---|
| 进行中 | 后台正在跑 | 取消（当前语料跑完后停） |
| 已中断 | 进程重启把它打断了 | **续跑** / 删除 |
| 失败 | 汇总阶段出错，逐语料结果还在 | **续跑**（跳过已完成的，直接重来汇总） / 删除 |
| 已取消 | 手动取消 | 续跑 / 删除 |

几条约定：

- **参数在创建任务时锁定**。续跑沿用它，不受顶栏当前配置影响——一轮里混两套参数，问题总数与任何一轮都不可比。
- **续跑前校验代码指纹**。中断往往正是因为改代码触发了重启，此时续跑会产出一轮前半段用旧代码、后半段用新代码的快照。界面会把两个指纹和已完成数量摆出来要一次确认；确认后仍要续，这一轮会被标记 `code_mixed`，在历史表格里带 `!`，提醒它不能与其它轮次直接比较。通常正确的选择是重新跑一轮。
- **单个语料失败不拖累整轮**，在详情页可以只重试那一个。
- **成功后中间结果自动清理**。数据已经存进正式快照与 `chunks.gz`，那份未压缩副本（一轮 6-10MB）没有留下的理由；中断与失败的会保留，那正是续跑的本体。

任务状态落在 `runs/.jobs/<job_id>/`，不是内存——内存态扛不住进程重启，而重启恰恰是最常见的中断原因。

解析任务（无论来自「解析文件」的批量上传还是「网页抓取」的批量解析）在服务端**串行执行**，同一时刻只跑一个：MinerU 是本机单实例服务，并行跑多个解析会把显存与内存打满，整体反而更慢。等待中的任务在列表里显示「排队中」，其中一个失败不影响后续任务继续执行。

解析任务支持**取消 / 删除 / 失败重试**（`labkit/parsing.py` 的 `cancel_task` / `delete_task` / `retry_task`）：

- **取消**：排队中的任务能真取消，直接从队列里撤回；运行中的任务只能软取消——MinerU 是单次阻塞 HTTP 调用，没有可轮询的检查点，当前这次请求仍会跑完，跑完后跳过自动入库并把状态标成「已取消」。
- **删除**：只删任务列表里的这条内存记录，不动已落盘的产物、不动已入库的语料（语料删除是独立功能）；运行中的任务不能直接删，需先取消。
- **重试**：每个任务是整份文件一次性解析，不像评估任务能按语料续跑，因此重试等于用原提交参数重新开一个新任务（新 `task_id`），旧记录留作历史。本地任务依赖上传目录里的原文件仍在；云端批量任务重试会把同一批文件重新整批提交。
- **批量选择**：任务列表每行带勾选框，配合表头全选框可一次选中多个任务，「重试选中」「删除选中」会对选中项逐个调用上面同一套单任务接口（`Promise.allSettled` 并发），不满足条件的（如运行中的删除、非失败/已取消的重试）会被对应接口拒绝，前端如实汇报成功与被跳过的数量，不会假装全部成功。

**本地解析的默认 backend 是 `vlm-engine`**，与本机 MinerU 的 VLM 部署一致。

桥接层 `chunklab_bridge.parse.resolve_mineru_config` 的内置默认是 `pipeline`——那是对齐
ragflow 生产的取值，实验室不该跟着它走，因此在 chunk-lab 侧统一覆盖（`paths.resolve_local_backend`），
桥接层本身不改。界面预填、表单兜底、`start_parse` 签名、下拉框首项四处都取这个值，
不再各自硬编码。优先级：

```
表单显式选择  >  环境变量 MINERU_BACKEND  >  labconfig.json 的 mineru_local_backend  >  vlm-engine
```

云端解析那条路径不受影响，它由 `mineru_cloud_backend` 单独控制（默认同为 `vlm-engine`）。

服务只监听回环地址，是开发时工具。基于 ragflow 虚拟环境里已有的 Flask，前端零构建、无外部依赖。

`serve.sh` 以端口占用而非 PID 文件判断状态，停止时结束**全部**占用该端口的进程——热加载下 Flask 重载器有父子两个进程，只杀子进程父进程会立刻重新拉起，看着停了实际没停。

## 原文对照支持哪些格式

预览页左侧显示原文，与右侧切片对照。点切片即在原文里定位。

| 格式 | 原文显示 | 点切片定位 | 说明 |
|---|---|---|---|
| PDF | 直接渲染 | **框出精确区域** | 块带 bbox |
| PPTX / DOCX / XLSX | 转 PDF 后渲染 | 翻到对应页，**多数情况下能补框近似区域** | 块只有页码、无 bbox，区域靠文字反查 |
| PNG / JPG 等图片 | 直接显示 | 框出精确区域 | 块带 bbox |

Office 文档由 LibreOffice 转成 PDF，复用同一套视图（缩放、翻页、定位、截图），
不必为每种格式再写一遍渲染。转换结果按源文件修改时间缓存：首次几秒，
之后毫秒级。没装 LibreOffice 时界面会提示 `brew install --cask libreoffice`。

图片刻意**不转 PDF**——转一道既糊又慢，而且图片的 MinerU 块本来就带 bbox，
直接显示才能做精确定位。

**MinerU 给 Office 块的坐标是退化值**（形如 `[2, 0, 0, 1, 1]`，宽高为零），
本身框不出块的位置。DOCX 更受限：它的 `page_idx` 全是 0，连页码都对不上，
点切片只能显示原文、翻不到具体哪一页。这是解析阶段的既有事实，不是这里的取舍。

**有页码时会用文字反查补一个近似高亮框**（`labkit/preview.py::locate_chunk_text`，
`/api/preview/<case_id>/locate`）：LibreOffice 转出的 PDF 通常保留真实文字层，
拿切片正文按自然行去对应页面做精确文字搜索，取每行开头一小段（太长容易跨越
PDF 渲染时的折行断点、太短又容易在页面上命中不止一处），命中恰好一处才采信，
多行命中取外接矩形。找不到（版式复杂、艺术字、图表里的文字）就如实放弃、
维持原来的纯翻页效果，不瞎猜坐标。这是近似框，不是真坐标——原理和生产 RAGFlow
给 DOCX 做的"渲染成文本后模糊匹配高亮"是一个思路，只是这边用的是 PDF 文字层
搜索，PPTX 也能覆盖到（生产给 PPTX 用 canvas 渲染，没有文字节点可搜，完全没有
这层效果，见对话记录）。前端 `focusChunkInPdf` 点切片时异步触发、按切片序号缓存
结果，找到了就调用画框的同一套 `pdfView.focus()`，找不到不影响已经完成的翻页。

图片样本能显示原文，但用 `naive` 切分器**切不出切片**——生产的 naive 只支持
pdf/xlsx/doc/docx/txt。要切图片得把「解析方法」改成 `picture`。

## 改完代码怎么看效果

```
改代码 → 运行评估（全量切一遍，存成一个版本）→ 预览页与规则质量页选那个版本看
```

评估会把**每个样本的完整切分结果**存进该版本的快照：正文、面包屑、页码、
版面坐标、以及那一版检出的全部问题。预览页顶部的「版本」下拉可以选任意
一版，读的是文件，不重新切分——上千切片的样本实测 3.5 秒。

**切片预览只看版本快照，没有「实时切分」这一档**。原因是标注按版本保存：
标注挂在某一版的切片上，而实时切分用的是当前代码，切出来的块与任何一版都
未必对得上，在那上面标注就说不清这条判定到底属于哪一版。要看代码改动的效果，
就跑一轮新评估——那才是"当前代码"的正式快照。

每一版都记着自己的代码指纹，下拉里直接标出「= 当前代码」还是「代码已变」。
改完代码没跑评估时，看着旧快照会误以为改动没生效，这个标注就是防它的。

删除某一轮会连带删掉它的快照、切分文本、Markdown 报告与索引记录；
若它正是当前基线，指针一并清空。

## 运行：命令行

```bash

./run.sh eval                      # 全量评估，出报告
./run.sh baseline                  # 建立回归基线
./run.sh eval --compare            # 改代码后：与基线比较指标升降
./run.sh eval --compare --set-baseline   # 确认改善后固化为新基线
./run.sh guard                     # 回归护栏：用最新版本核对上一版的人工判定
./run.sh guard --run <版本> --base <版本>   # 指定用哪两版比
./run.sh guard --todo --why        # 只看待办，并附误报共性分析
./run.sh smoke <产物> <文件名>      # 单产物连通性调试
```

### 改检测规则的顺序

规则是靠人工标注来验证的，不是靠感觉。正确顺序：

```bash
# ... 修改 labkit/detectors.py ...
./run.sh eval               # 1. 跑一轮新评估：产生新版本，标注自动继承并重判
./run.sh guard --todo       # 2. 用新版本核对上一版的判定
```

护栏把标注变成断言：标为**误报**的应不再命中，标为**确认**的应仍能命中。
只有出现「回归」才算失败——那说明改动碰坏了本来能检出的东西；「待修正」是
还没改到的待办，「仍未覆盖」是人工提出、规则尚未实现的需求，都不该拦住一次改动。

### 标注按版本独立保存

**每一次人工判定都归属于一个版本**，存在 `annotations/<版本>/<样本>.json`。
在哪一版的切分结果上标的，就属于哪一版；换个版本看，看到的是那一版自己的账。

这是必须的。同一段正文在不同版本下会被切成不同的块、被不同的规则命中，
「这条规则报得对不对」离开具体版本就没有答案。共用一份标注的话，上周标的
一条误报这周已经修好了，却照样压低准确率，等于拿旧账算现在的成绩；
生成的任务书里还会列着已经不存在的问题，让人去改一个空气。

每条标注记两样东西，必须分清：

- **人工判定**（`verdict`）：确认是问题 / 误报 / 漏报，只有人能改；
- **成立状态**（`status`）：这条判定在本版本下还成不成立，写入或继承时按该版本
  快照的命中情况自动算出来。

规则质量页展示的就是 `status`：

| 计数 | 含义 |
|---|---|
| 仍在误报 | 这一版还没修好的，**这才是待办** |
| 已修复 | 上一版标为误报、这一版已不报，不计入准确率 |
| 仍能检出 | 确认是问题且这一版仍能检出 |
| 回归 | 上一版能检出、这一版检不出了，**唯一算失败的一档** |
| 已覆盖 | 上一版是漏报、这一版已能抓到 |
| 标注已失配 | 找不回对应切片，需重做，排除在统计外 |

因为状态是现成的，页面只读该版本的标注目录，毫秒级返回，不再重切任何东西。

### 新版本自动继承上一版的标注

跑评估产生新版本时，上一版的标注会自动搬过来，并按新快照逐条重判：
误报还报着就仍是待办、不报了就转成「已修复」；确认能检出的检不出了就是「回归」。
序号与摘要一并更新成新版本的，`origin` 记着它继承自哪一版。

没有继承的话，每跑一轮几百条标注就要重标一遍，准确率曲线也会断档；
而共用一份标注又说不清「这条误报到底改好了没有」。继承正是这两者的交点：
判定还是人那一次的判定，成立与否按新版本重算。你在新版本上重标任意一条，
它就转为本版本自标，不再被继承值覆盖，且只影响这一版。

跨版本对齐**先按序号、再按正文摘要**：切分逻辑没动的块序号相同，摘要能对上
就是同一块；只有切分确实变了才退回摘要模糊匹配。这一步不能省——只靠模糊匹配的话，
相邻块开头相同（同一标题下的连续段落，面包屑前缀一致）会让标注认领到错误的块，
把好端端的判定算成回归。两种方式都找不回时记为「标注已失配」，提示该条需重做。

**规则质量页上的每一项都跟着选定版本走**，没有例外：统计数字、误报共性归纳、
点数字看到的明细、单条规则的优化报告、整份任务书、框选区域。点明细跳到切片
预览时，预览页也会切到同一版本——否则看到的切片与刚才的数字对不上。

**原文上圈出的区域**同样按版本保存、同样会继承，但**无法自动核对**：
切分器压根没在那儿产出块，也就没有「该规则是否仍命中」可判，是否已解决由人自己看。

### 优化任务书（直接交给 Claude）

「规则质量」页的**生成优化任务书**，把当前全部待办打包成一份 Markdown：

```bash
./run.sh guard --report 任务书.md    # 命令行同样能出
./run.sh guard --report              # 不给路径则打印到标准输出
```

内容按「能否自动验证」排序：任务一是误报（有护栏兜底，改完立刻知道对不对），
任务二是已有规则的漏报（调判据或阈值），任务三是人工提出的新需求（要新写代码，
无护栏兜底），任务四是框选出来的漏切区域（多半出在解析或切分阶段，不是检测规则）。

每条都带上规则的**当前源码**、反例**在该版本下的真实命中证据**、人工判断的原因，
开头写明基于哪个版本，以及代码位置、`Finding` 字段约定与验证命令——拿到的人不必
回头再问。整份复制给 Claude 就能动手改。已经修好的问题不会出现在里面。

### 单条规则的优化报告

「规则质量」页每条规则后的「生成优化报告」，产出一份可直接拿去改代码的 Markdown：
规则的**当前实现**（函数源码与相关正则常量，从运行中的模块直接取，不会与代码脱节）、
每条反例**在该版本下的真实命中证据**（从该版本快照取得，与统计同源）、人工判断的原因、
以及改完怎么验证。整段复制给模型即可动手改。

实测 `markdown_residue` 的报告一眼看出问题：8 条误报的命中证据全是 `__name__`，
即 Python 的 dunder 被 `__[^_\n]+__` 当成了 markdown 强调。

页面上所有统计数字都可点击：点误报数看全部反例、点需求次数看在哪些切片上提的，
点任意一条跳回切片预览并定位到那块正文。框选出来的区域单独汇总一块，
点一条跳回原文视图并滚动到该区域——它不属于任何切片，不会出现在规则统计里。

一条规则命中上百个切片时，逐条判定不现实。在切片预览里点某个问题类型筛选后，
筛选栏下方会出现整类批量判定条，可一次把该类下**尚未标注**的切片全标为误报或
全确认是问题，也可整批撤销。已标注的切片一律跳过——批量是为了省去重复点击，
不该悄悄推翻此前逐条细看后给出的判断；界面上会直接标出「N 个已标注，写入时跳过」。

批量写入的问题类型记为**当前筛选的那一类**，而不是切片命中的第一条规则。一个切片
可以同时命中多条规则，按命中顺序归类会把判定算到别条规则头上，污染准确率统计。

常用选项：

| 选项 | 说明 |
|---|---|
| `--case <id>` | 只评估指定样本，可重复，用于针对单个文档快速迭代 |
| `--children-delimiter` | 父子分块分隔符，**对切分粒度影响极大**，见下文 |
| `--chunk-token-num` | 覆盖 token 预算 |
| `--top N` | 每类问题展示 N 条样例证据 |

全量评估 13 个样本、5608 个原始块约 **14 秒**——同样的内容走真实解析要几十分钟，这个差距就是整套方案能持续迭代的前提。

`run.sh` 固定使用 `ragflow/.venv/bin/python` 的绝对路径，不依赖当前终端激活了哪个虚拟环境，且**绝不使用 `uv run`**（避免触发 `uv.lock` 解析并静默改写环境）。

## 设计要点

离线驱动**不写任何 stub**，直接构造真实的 `MinerUParser` 并调用生产函数 `chunk_mineru_blocks`，保证离线结论与线上行为零偏差。三条依据均已在 ragflow 源码中核对：

1. `MinerUParser.__init__` 只赋值属性、不做网络调用，可无参构造；
2. `chunk_mineru_blocks` 内所有 `crop` 调用点都有 `page_images` 守卫，不提供页面图像即走"无截图"分支，与生产的 Office 路径行为一致；
3. `tenant_id` 传 `None` 时 `get_vision_model` / `get_chat_model` 直接返回 `None`，不加载 LLM、不 import `api.db`、不连数据库——因此离线结果确定可复现。

## 阶段一：保真度验证结论（已通过）

用 `tmp/pdfs/mineru_two_column_e2e_output/` 的双栏 PDF 产物离线重放，与历史生产 e2e 结果 `mineru_two_column_e2e_chunks/summary.json` 逐块比对：

- 喂给切分器的 blocks 完全一致（23 个，`text_level` 分布相同），确认产物层无偏差；
- 父块正文与生产 chunk 逐字吻合（如 `> 2 评估方法` + `[P03] 本样例采用 A4 纵向页面…`）；
- 唯一差异是面包屑分隔符（生产为换行、当前代码为 ` > `），属 summary.json 是历史产物、面包屑格式后来改过的代码演进，非离线偏差。

PPTX 路径同样验证通过（40 chunk，含 9 个表格，位置/页码/面包屑齐全）。

### 关键发现：`children_delimiter` 是切分粒度的主开关

同一份产物，仅改这一个参数，结果差异巨大：

| `children_delimiter` | chunk 数 | 平均长度 | 说明 |
|---|---|---|---|
| 空 | 14 | 127 | 每个原始段落独立成块 |
| `\n` | 14（子块） | 128 | 5 个父块，按换行拆成 14 个子块 |
| `‡`（正文中不存在） | 5 | 306 | 子拆分不切割，即父块粒度 |

机制在 [`mineru_chunker.py:1494-1498`](../ragflow/rag/app/mineru_chunker.py#L1494) 的合并边界判定：默认模式下"同标题的不同原始段落也必须独立成块"，父子模式下只有标题变化才断开。

两个必须记住的契约：

- **离线驱动必须复刻 `naive.py` 的 `children_delimiter → 正则` 转换**（含 `unicode_escape` 还原与反引号自定义分隔符），否则同一份产物会得到与生产迥异的结果；
- **父子模式下返回的全部是子块**，父块全文挂在 `mom_with_weight` 字段上。评审器必须据此区分口径，否则会把子块的短长度误判为切分过碎。

## 阶段二～三：检测器、语料库与回归防护（已完成）

### 语料库

13 个样本、5608 个原始块，覆盖 PDF（双栏／法律／年报／专利）、PPTX、DOCX、XLSX。

同一文档的重复解析副本只收一份，但**同源不同 backend 的产物刻意保留为对照**（`law_bill_hybrid` 137 块 vs `law_bill_vlm` 111 块）——块数差异这么大，切分逻辑对它是否鲁棒本身就该被测。

#### 动态启停：选哪些样本参与评估

语料库页每行一个勾选框，另有「全部启用／全部停用／反选」。状态存在各样本的
`case.yaml: enabled`，缺该字段一律视为启用（存量样本不用改）。

**停用不是删除**：产物、历史轮次、已有标注全都留着，只是「运行评估」不跑它。
真要删掉语料见下一节，那是不可撤销的操作，且会连带删掉它的全部人工标注。
这条边界体现在代码里——`load_cases()` 默认返回全部，只有全量评估传
`for_eval=True`；按 id 取单样本、查文件名、给标注补文件名这些调用都必须能
看到被排除的样本，否则排除一个样本会连带让它的历史标注失去文件名。命令行
`./run.sh eval --case <id>` 显式点名时也不受影响：开关管的是「默认取哪些」，
不是「禁止访问」。

#### 删除语料：单个与批量

表格最左侧多一列**选择框**（与「启用」列分开，两者语义不同：一个决定「删哪些」，
一个决定「评估跑哪些」，共用一个勾选框会把不可撤销的操作和日常开关混在一起），
表头可全选，工具栏的「删除选中 N 项」按钮直接带出数量；每行末尾另有单个删除。
两者共用同一段二次确认，确认框里列出样本名与将要删掉的内容。

删除会连带清掉三样**该样本专属**的东西：

- `corpus/<case_id>/`：产物副本、`middle.json`、`case.yaml` 与 `images` 软链；
- `sources/<case_id>/`：为原文对照与截图关联上来的原始文件；
- **全部版本下**它的人工标注（切片标注与区域标注）。语料都没了，这些判定既无从
  复核，也不该继续压着某条规则的准确率。`annotations/_migrated_backup/` 不动，
  那是迁移时留的最后一份原始记录。

**历史轮次快照一律不动**（`runs/*.json` 与 `*.chunks.gz`）。那是「那一轮确实跑出了
这些结果」的事实记录，重写它会让趋势图、轮次对比与已生成的 Markdown 报告数字全部
对不上。预览侧本来就有兜底：样本从语料库消失后，历史版本里它的切片照样能看，
只是没有文件名、因而失去原文截图。

`sources/converted/` 的转换缓存也不动——那里按「文件名 + 源文件修改时间」命名，
可能被同源不同 backend 的另一个样本共用，且随时可重新生成。

删 `corpus/<case_id>/` 时**绝不能跟随符号链接**：`images` 指向 `mineru_out/` 里的
真实产物，跟随删除会把 MinerU 的解析结果一起毁掉。`shutil.rmtree` 只解除链接、
不进入其指向的目录；代码里另外断言样本目录本身不是软链，防止有人手工把整个样本
目录做成软链后被整体误删。

接口是 `POST /api/corpus/delete`，单个删除也走它。与 `/api/corpus/enabled` 的关键
区别是 `case_ids` **必填且不得为空**：那边省略即「全部」是为了全选/全不选，而删除
不可逆，「参数漏传就把语料库清空」不是能接受的默认行为。

#### PPTX 默认不参与评估

`EVAL_EXCLUDED_EXTS = {".pptx", ".ppt"}`，与停用开关一样只作用于 `for_eval=True` 这条路径。

原因是**切块契约不同**：PPTX 走 `slide_mode`，严格按幻灯片每页一块；其余文档走
「长段落独立成块、短段落合并到 token 预算」。用同一套检测规则去衡量 slide_mode 的产出，
报出来的多半是契约差异而不是缺陷——此前 `missing_breadcrumb` 对 pptx 的 13 条误报
（整页成块、无标题页天然没有面包屑）就是典型。

仍可用「试切」页签看 pptx 切得怎么样：试切列的是语料库全部样本，不受评估口径约束。

停用期间它的标注**原样保留并标为「本版本未评估」**（状态 `skipped`），不计入准确率
与召回率、不进优化任务书，重新启用后自动恢复生效。这与「标注已失配」严格分开——
后者是标注对不上切片、需要人去重做，而前者什么都不用做。混在一起的话，停用几个
样本就会凭空多出几百条看着像数据损坏的失配记录。

**切片预览的样本列表来自「当前选中版本实际评估过哪些样本」，与语料库的启用状态无关。**
两者回答的是不同的问题：启用状态说的是「下次评估跑哪些」，预览要看的是「这一版跑出来
是什么样」。拿启用状态过滤会有两种错——停用后还没跑新评估时，当前版本里明明有它却被藏起来；
新导入还没参与评估的样本会被列出来，点开必然报「快照里没有这个样本」。

数据源是 `/api/runs/<run_id>/cases`，即那一轮报告里的逐样本记录，列表直接显示该轮的
切片数与问题数，切分失败的样本也会标出来。切换版本会重建列表——两版评估的样本集可能不同；
当前打开的样本不在新版本里时右侧清空并提示重选。

#### 试切：只想人工过目一个文件，不动任何指标

顶栏的**「试切」页签**即入口，进去就是试切态：左侧直接列出语料库全部样本
（含未评估、已停用、pptx 这类默认不参与评估的类型），点一个即用**顶栏当前参数**实时切分。
不需要任何模式切换，也不必先跑评估。

**入口为什么是独立页签**：它最早只是「版本」下拉的最后一项，而那个下拉要**选中样本之后**
才渲染出来；后来提成「切片预览」页顶部的常驻按钮，但页面默认仍是版本模式——左侧只列
该轮评估过的样本，没评估过的文件必须先发现并点那个按钮才看得到，等于把「看还没进评估的
文件」藏在一次模式切换后面，实际使用中仍然没人找得到。现在两者各占一个页签：
**切片预览看快照，试切看当前参数**，进哪个页签就是哪种模式，不再有隐式状态。

实现上两个页签**共用同一块预览面板 DOM**（进页签时整块搬过去），而不是复制两份：
面板绑死在一组固定 id 上、PDF 渲染器又是单例，复制会让 id 重复、渲染器只认第一份，
标注、截图、滚动定位全部错位。搬家用 `appendChild`，已渲染的页面画布与事件绑定原样保留。
从试切切回切片预览时，会退回**进入试切之前看的那一版**（那一版已被删才回落到最新一轮）。

它的定位是「我就想看看这个文件切得怎么样」，因此**不产生任何持久状态**：
不写轮次、不进索引与趋势图、不参与基线对比与标注继承。正因为压根不落盘，
才不存在「要不要把它从指标里排除」的问题。

代价是**不支持标注**——切片标注与框选区域都必须挂在版本上才说得清「这条判定属于哪一版」，
而版本正是整套统计与跨版本继承的地基。试切没有版本可挂，所以标注按钮、整类批量判定、
原文框选在试切页签下一律不提供，「版本」下拉也不出现（它只列真实轮次，不再混进试切项）。
要记录判定，把该样本纳入评估、在对应版本上标。

**附带解决了调参**：顶栏参数原本只作用于「运行评估」，改个 `chunk_token_num` 要跑全量
才知道效果。试切让它在单个样本上立刻可见——改完参数重新点一下左侧样本即可。

速度取决于增强项：纯切分是秒级的（决策树.pptx 2.2 秒、1107 切片的年报 3.8 秒），
但图片 VLM 描述与表格摘要按图表数量逐个调模型，同一个 pptx 开着增强项要 **122 秒**。
试切跟随顶栏配置；这两个开关现已默认关闭，图表多的文件不必再手动去关。

### 检测器

16 个规则检测器，全部在 `detectors.py` 的 `ALL_DETECTORS` 登记表中，新增只需追加一项。

严重度分三档：`high` 内容层缺陷（句子截断、表格破损、表格被拆散、乱码、噪声残留）、`medium` 质量问题（碎片块、内容重复、列表被拆散、指代缺失上下文、图注公式脱离、标题孤块、标题与正文分离、markdown 残留、图片空壳）、`low` 体验问题（缺面包屑、缺定位）。

曾有「字间空格」检测器，经判定属正常排版（封面艺术字、字间距样式）已移除。

#### 判据要与生产切块契约对齐，而不是拍一个阈值

生产的切块契约变过之后（长段落独立成块、同小节内短段落合并到 token 预算），
两个检测器的固定阈值就不再表达契约，必须改成**契约派生**的判据：

- **`undersized_chunk`**：从「正文短于 15 字」改为「**同一小节内相邻块也短于 200 字，
  两者本该合并**」。固定字数表达不了「短得合理」与「短得有问题」的区别——实测年报里
  79%~85% 的短块是所在小节的唯一一块，无邻居可合，短是文档结构使然。
  阈值 `STANDALONE_MIN_CHARS = 200` 必须与生产的
  `mineru_chunker.STANDALONE_PARAGRAPH_MIN_CHARS` 同步。
- **`duplicate_content`**：**面包屑不同一律不算重复**，只在同一标题小节内判定。
  这不是经验规则而是结构性结论——切块器的 overlap 只在同一标题路径、同一原始段落的
  相邻分片之间生成（见 `_merge_text_units` 里 `prev_chunk_last_path == current[0].path
  and prev_chunk_last_order == current[0].order`），**跨标题根本产生不出重复内容**。
  所以跨面包屑的正文雷同只可能来自文档本身：年报每个小节标题下都有一句
  「□适用 √不适用」，那是披露格式，不是缺陷。
  （更早的版本只跳过「跨小节 *且* 当前块是所在小节唯一一块」的，附加条件是多余的。）
- **`list_split`**：判定前先过一道**可合并性**——「同一标题下没有合并到一起」本身
  不构成缺陷。生产对同标题相邻段落只有两个断开理由：任一侧达到 200 字独立成块阈值
  （`_is_standalone_unit(前) or _is_standalone_unit(本)`，注意是 `or`），或合并后超
  token 预算。命中任一条时列表跨块都是契约使然。不加这道判断，长段落组成的编号列表
  会被成片误报——典型如「（2）存货减值的估计…」478 字接「（3）长期资产减值的估计…」，
  两个都是完整的独立语义单元。

这三条判据带来的实测差异（2026-08-09，34 个样本）：

| 检测器 | 加判据前 | 加判据后 | 被排除的是什么 |
|---|---|---|---|
| `list_split` | 76 | **12** | 64 条长段落编号列表；留下的 12 条全是真问题（同一份操作手册里「4. 双击RA证书」「5. 点击下一步」这类短步骤被逐条切开） |
| `duplicate_content` | 18 | **0** | 全部是跨章节的「□适用 √不适用」 |
| `dangling_reference` | 17 | **8** | 9 条位于独立标题小节首块的指代（判据见下） |
| `heading_tail` | 10 | **1** | 9 条目录页末行（判据见下） |

- **`dangling_reference`**：位于标题小节**首块**且带面包屑的指代不再算缺失上下文。
  首块的指代必然跨小节——同小节没有更靠前的块可指；而跨小节意味着标题已经切换话题，
  **面包屑本身就是新的上下文锚点**：检索命中「上述与合同成本有关的资产…」时，
  面包屑「… > 4.合同成本减值」已经说清这段在讲什么。反过来，小节第二块及以后的指代
  指向的是同一小节被切走的前一块，那才是切分造成的断裂，仍要报——
  典型如「上图输入框中的输入信息参见下表。」，上图就在同小节的前一块里。
  实测 17 条按小节位次分：首块 9 条（全部豁免）、第 2~5 块 8 条（全部保留）。
- **`heading_tail`**：末行是**目录项**（正文 + 引导点或多空格 + 页码，如
  `第八节 财务报告....48`、`第八节 财务报告 …… 41`）时不算标题。目录页每一行都形似标题
  ——「第八节 财务报告」本就是章节名——但它们指向的正文在几十页之外，本来就不该跟在
  目录后面，谈不上「被切开」。实测 10 条命中里 9 条是这一形态，且这 9 条的面包屑末级
  全是「目录」、整块 8 行全为目录样式；唯一保留的那条目录样式行为 0，是真的标题掉队。

#### 「小节里就这一句话」的极短块：有意不报

全语料有 509 个正文短于 10 字、且**所在小节只有这一块**的块（几乎全是「□适用 √不适用」）。
它们入库确实没有检索价值，但**切块器无从修复**：标题是硬边界，跨标题合并不在契约内。
经判定这类**不计入问题**——报出来既指不出可执行的修法，又会以 4 倍于当前问题总数的
体量淹没其它信号。若将来决定放开「过短小节并入相邻块」，那是改切块契约的事，
届时再新增一类检测器，而不是把它塞进 `undersized_chunk`（两者语义不同：
后者是「本该合并却没合并」的实现问题）。

**这么改的收益不只是少报误报**。判据与契约对齐后，检测器从经验阈值变成了可证伪的断言：
`undersized_chunk` 随后就报出两处「本该合并却没合并」，追查下去分别是表题吸附越界、
以及 MinerU 把「□适用 不适用」标成了标题——后者是个影响 11 个样本、97 处面包屑的
生产缺陷，此前从未被发现。缺陷修好后这些命中自动归零。

### 回归防护：运行历史

每次评估都存成**不可变快照**（一个 run），任意两轮之间都能对比。基线不再是一份独立数据，只是**指向某一轮的指针**——因为单一基线文件一旦更新，之前的历史就没了，无法回答「这几次改动累计效果如何」「哪一次引入了这个回归」。

```bash
./run.sh eval --label "修复 DOCX markdown 残留"   # 跑一轮，自动存入历史
./run.sh runs                                    # 看全部历史轮次
./run.sh runs --compare baseline latest          # 对比任意两轮
./run.sh baseline <run_id>                       # 把某轮设为基准（不必重跑）
```

轮次引用支持三种写法：`baseline`（当前基准）、`latest`（最新一轮）、具体 `run_id`。

**每轮记录代码指纹**——对 `mineru_chunker.py` / `mineru_parser.py` / `mineru_noise.py` 做联合内容哈希。这比 git commit 更准：改了没提交时 commit 不变，只有哈希会变。没有它，历史轮次不知道对应什么代码状态，对比就失去意义。

**对比前自动校验可比性**。参数或语料不同的两轮，数字并列会直接导致误判，因此会显式警告：

```
⚠️  这两轮不完全可比：
    · token 预算不同（512 vs 256），切分粒度本就不同，数字不能直接归因于代码改动
    · 两轮的被测代码完全相同，指标差异并非来自代码改动
```

这两条合起来就说清了：那次「劣化 +16」根本不是代码问题。

### 切分文本快照：为什么必须存

每轮同时保存**当时的切分文本**（`runs/<id>.chunks.gz`）。这不是可选项：离线驱动调的是**当前**代码，代码一改，旧轮次的切分结果就再也无法重现。不存下来，历史轮次只剩统计数字，看不到那时文本被切成了什么样。

体积可控：3272 个切片的完整正文，gzip 后约 **335 KB**，跑 20 轮才 6.7 MB。

有了它才能做**文本级对比**——问题数只能说明"多了 6 条截断"，文本对比才能说明"边界从哪挪到了哪"。实测 token 512→256：

```
切片 89 → 97，内容未变 84，变化 13
[修改] #4 → #4
  前：附件4\n<table>…
  后：附件4（分片 1/2）\n<table>…
```

表格被拆成了「分片 1/2」「分片 2/2」，一眼可见。配对同样按内容而非序号——按序号比会把 89 个切片几乎全算成变化。

切片预览页也可切换数据来源：**实时切分（当前代码）** 或**任一历史轮次的快照**。

存储上，`runs/*.json` 是报告（含 findings 明细），`runs/*.chunks.gz` 是切分文本，两者体积大不入库；`runs/index.json` 是轻量索引（含各轮各检测器命中数，**入库**），所以指标趋势可以长期追溯。

对比同时输出**命中数**与 **chunk 数**两个维度，缺一不可。实测把 `chunk_token_num` 从 512 降到 256：

```
xlsx_9sheet    命中 0→0 (+0)    chunk 65→208 (+143)
```

命中数完全没变，切分粒度却暴增 3 倍。只盯问题数会彻底漏掉这类回归。
